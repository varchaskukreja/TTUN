# Definition-expression export audit

The existing export walk in `tools/class_attribute_exports.py` handles FunctionDef/AsyncFunctionDef by immediately recursing into `body` and continuing. It therefore skips defaults, decorators, argument annotations and return annotations. Its body recursion is static evidence discovery, not a claim those statements execute during import. The correction should preserve that distinction.

The standalone `tools/definition_expression_exports.py` augments existing evidence without editing the walker. Nine tests cover positional/keyword defaults, decorators, annotations, future annotations, class-local default names, nested function timing, lambda defaults versus bodies, imported aliases, and class-valued binding captures.

In Python 3.13, ordinary defaults and decorators are evaluated when a definition executes. Ordinary non-future function annotations are also evaluated then; future annotations store strings instead. Type-parameter bounds/defaults have lazy annotation-scope semantics and require separate modeling. A nested definition executes when its enclosing callable reaches it, not when the module imports; lambda defaults execute when that lambda expression is evaluated, and its body executes later. Inspecting a header must not blindly ast.walk into a lambda body. Annotation strings can later be explicitly evaluated by consumers; omission from eager captures does not certify absence of a reflective dependency.

CopyBudget provides four direct, resolved captures: MAX_COPY_FACTOR and MIN_COPY_BUDGET in its constructor's class-local default scope, and the same fields qualified through CopyBudget in the free merge_subqueries defaults. In the pinned module these names are the declared class fields, with no intervening class-binding reassignment. A method's default is stored on a function object and can be observed without a receiver; conservatively exporting its source field is justified. A more precise downstream function-consumer edge would need to include metadata inspection and inherited/aliased methods too.

The prototype resolves module absolute imports and explicit class fields, and adds wildcard evidence for a captured class object (including a known class-valued attribute). It is not a complete symbol resolver: relative imports, arbitrary local aliases, later rebinding, lexical shadowing and dynamic decorators remain unresolved. No missing evidence can authorize narrowing. A production correction must either preserve conservative fallback for these cases or provide a real binding proof. The existing static walker likewise is incomplete; this supplement repairs identified omissions, not all Python dataflow.

The broad alternate map also considers class bases and metaclass keywords. These can trigger wildcard exports where an inherited nested class is not resolved precisely. Such flags are intentionally conservative but excessive; the existing inheritance graph already handles many class-base dependencies. Review should separate the minimum function/lambda-header correction from this broader class-header experiment before integration.

Alternate-map sample evaluation used real ImportGuard collection results shared across paired selectors, with the ordinary factory proof path. Both had zero sample misses. Scheduled cost changed 256.055s to 281.634s, entirely from one sample selection increasing 171 to 1620 tests. This is offline evaluation only; no answer data entered the analyzer. Coverage owns independent physical CopyBudget testing, and no miss is claimed here. Exact hashes, added flags and artifacts are recorded in validation/research-definition-expressions.json. No active helper or production map was edited.

## Scope-isolated follow-up

The helper now defaults to function/lambda headers only. `--include-class-headers` enables the earlier broad experiment. Ten tests pass. The minimal variant adds 13 recognized captures and retains all four CopyBudget reads. Paired actual guards pass 4/4; sample cost stays 256.055s with zero selection differences and zero misses. The earlier +25.579s arose from Fabric.Tokenizer inheriting TSQL.Tokenizer, represented too broadly as a TSQL wildcard; it was unrelated to function headers.

Same-name fields inside comprehension/lambda scopes may be misresolved as class-local: this can add conservative false positives. Relative imports, local aliases and shadowing are still unresolved. Neither variant is a complete binding analysis or an absence proof. The validation JSON preserves the historical broad hashes and adds current helper/minimal-map hashes.
